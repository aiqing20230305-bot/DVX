# 技术决策：延期questionnaire/testing参数命名统一

**决策日期**: 2026-04-10  
**决策者**: 自动迭代系统（Claude Opus 4.6）  
**状态**: ✅ 已决策  
**影响版本**: v2.2.4 → v2.3.0

---

## 📋 背景

### 任务描述
将questionnaire和testing模块的API参数从snake_case统一为camelCase，与其他API保持一致。

**来源**: v2.2.0完成kb.route.ts的命名统一后，识别到questionnaire/testing模块仍使用snake_case

**优先级**: P3（代码规范提升，不影响功能）

---

## 🔍 评估过程

### 工作量分析

**扫描结果** (2026-04-10 18:48):
```bash
questionnaire.route.ts: 433行代码，41处snake_case参数
testing.route.ts:       266行代码，42处snake_case参数
总计:                   699行代码，83处需要修改
```

**参数映射**:

Questionnaire模块（7个参数）:
- trigger_type → triggerType
- trigger_value → triggerValue
- question_type → questionType
- question_text → questionText
- order_index → orderIndex
- questionnaire_id → questionnaireId
- question_id → questionId

Testing模块（7个参数）:
- session_id → sessionId
- user_name → userName
- user_role → userRole
- user_email → userEmail
- action_type → actionType
- start_time → startTime
- end_time → endTime

### 风险分析

#### 1. 高错误风险
- **83处手动修改**：容易遗漏或写错
- **两个模块交叉引用**：questionnaire_triggers表关联两个模块
- **TypeScript类型定义**：需要同步更新

#### 2. 缺乏测试保障
- **无自动化测试**：questionnaire/testing模块没有单元测试或E2E测试
- **手动测试成本高**：需要测试所有API端点和边缘情况
- **回归风险**：可能破坏现有功能但无法快速发现

#### 3. 低投入产出比
- **P3优先级**：不影响核心功能
- **辅助模块**：使用频率低，不在关键业务路径上
- **用户无感知**：修改仅提升代码规范，用户体验无变化
- **工作量vs收益**：83处修改 vs 仅提升代码一致性

#### 4. 时机不佳
- **连续迭代疲劳**：已完成3轮迭代（v2.2.1-2.2.3），耗时45分钟
- **系统已稳定**：v2.2.3功能完整，无P0/P1/P2问题
- **没有紧迫性**：可以等待更合适的时机

---

## 🎯 决策

### 决定：延期至v2.3.0

**原因**:

1. **保护系统稳定性**
   - v2.2.3已经生产就绪，功能完整
   - 83处修改风险高，不应在小版本中执行

2. **遵循工程最佳实践**
   - 大规模重构应有充分测试保障
   - 应在feature分支中进行，代码审查后合并
   - 应作为计划内任务，而非紧急修复

3. **优先级管理**
   - P3任务不应挤占P0/P1/P2的资源
   - 当前无更高优先级任务不代表应执行低优先级任务
   - 应等待真正需要的时机（如用户反馈或新功能需求）

4. **投入产出比**
   - 预计耗时：40-60分钟（包括测试）
   - 收益：仅代码规范统一
   - ROI低，不适合当前执行

## 🎯 替代方案

### 方案A：延期至v2.3.0（已选择）✅

**优点**:
- 风险最低
- 有充分时间准备
- 可以系统性重构
- 保持v2.2.x稳定

**缺点**:
- 代码规范短期内不统一
- 新开发者可能困惑

### 方案B：立即执行（已拒绝）❌

**优点**:
- 快速完成代码统一

**缺点**:
- 高错误风险（83处修改）
- 无测试保障
- 可能引入回归bug
- 不符合工程最佳实践

### 方案C：分阶段执行（备选）

v2.2.4修改questionnaire（41处）  
v2.2.5修改testing（42处）

**优点**:
- 风险分散
- 每次修改量减半

**缺点**:
- 仍然缺乏测试保障
- 两个版本之间不一致
- 总耗时更长

## 🎓 经验教训

### 对自动迭代系统的启示

1. **优先级管理**
   - P3任务不应在紧急迭代中执行
   - 应设置"连续迭代次数上限"（建议3次）
   - 大工作量任务应评估后决定是否执行

2. **风险评估**
   - 修改点数>50 → 高风险
   - 缺乏测试 → 延期补充测试
   - 辅助模块 → 降低优先级

3. **时机选择**
   - 系统稳定时不应强行修改
   - 技术债应在大版本中集中清理
   - 应等待合适的窗口期（如新功能开发时）

4. **工程实践**
   - 大规模重构必须有测试保障
   - 应在feature分支中进行
   - 代码审查不可省略
